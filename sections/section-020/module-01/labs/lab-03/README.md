# Revoke A Leaver's Access Everywhere

The learner removes every access of the person `leaver`: the node group `flight-ops`, a sudo rule file in `/etc/sudoers.d`, a RoleBinding and a ClusterRoleBinding for the user name `leaver`, the password and an SSH key in `authorized_keys`. The account `crew-member` must keep the same kinds of access.

The lab runs in a QEMU virtual machine built from the pinned CKS image `ghcr.io/astrona-io/ubuntu-qcow2-image:24.04-cks-20261118-{ARCH}`. `vm/install.sh` (generated by `scripts/ci/vm-lab.py`) builds a one-node kubeadm cluster, copies the lab to `/opt/astrona-lab` and runs `bootstrap/setup.sh`. Setup applies `bootstrap/manifests/start.yaml`, creates the accounts, the group, the roster and both sudoers files, and generates an SSH key pair for `leaver` in `/var/lib/astrona-lab-033-020-01-03`. The sudo outcome uses the real `sudo -l -U leaver` and `visudo -c`. The RBAC outcome uses strict `kubectl auth can-i --as=leaver` answers. The lock outcome also makes a real key login as `leaver` to `127.0.0.1`, because with `UsePAM yes` a locked password alone does not stop a key login (seen live).

Live run on 2026-11-18 (arm64, hvf): `astrona test -c lab-03` ran `testing/verify-start.sh`, which proved that all four outcomes fail on the starting state. After `solution/apply.sh`, all four outcomes passed (`4 passed, 0 failed`, `PROCTOR: PASS`) in about 70 seconds, VM start included. Every command output in `solution.md` comes from a manual walkthrough in an `astrona run` VM of the same image that day.
