# Bind A Host-Network Service To Loopback

The lab runs a one-node kubeadm cluster in a QEMU VM (`runtime.type: qemu`), because the grader reads listeners with `ss` on a real node. `vm/install.sh` builds the cluster and runs `bootstrap/setup.sh`, which starts `node-local-server` on the host network bound to `0.0.0.0:19090` and the client pod `shuttle`. The learner works as `student` through `astrona ssh astro-ats-033-lab-030-01-01` and replaces the pod so that it binds `127.0.0.1:19090`.

Outcomes (1 point each):

- `loopback-listener`: `ss -tlnH 'sport = :19090'` on the node lists `127.0.0.1` and no wildcard or node address.
- `node-address-refused`: `wget` from `shuttle` to the node InternalIP on port 19090 fails with `Connection refused`.

Both outcomes also need `node-local-server` Ready on the node and `curl http://127.0.0.1:19090/` on the node to return 200. The graders do not compare the pod spec, so any command that binds loopback passes.

The files under `vm/` are generated by `scripts/ci/vm-lab.py`; regenerate them after any change to a lab file. Run `astrona test` on this folder: `vm/verify-start.sh` checks that every outcome fails on the starting state, then the reference solution is applied and every outcome must pass. Live run on 2026-11-18 (QEMU image `24.04-cks` build 20261118, Kubernetes `v1.35.10`): `astrona test` ended with `PROCTOR: PASS` (2/2). In a separate `astrona run`, `shuttle` read the page at `10.0.2.15:19090` on the start state; after the pod was replaced, `ss` showed `127.0.0.1:19090`, loopback returned `200` and `shuttle` got `Connection refused`.
