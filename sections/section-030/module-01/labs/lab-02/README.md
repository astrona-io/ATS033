# Block A Host Port With ufw

The lab runs a one-node kubeadm cluster in a QEMU VM (`runtime.type: qemu`), because it turns on `ufw`, the host firewall of the node. kind nodes have no `ufw`. `vm/install.sh` builds the cluster and runs `bootstrap/setup.sh`, which starts `node-metrics-server` on the host network on `0.0.0.0:19091` and the normal pod `shuttle`. It then leaves `ufw` inactive with the default policies `allow incoming` and `allow routed`, so turning `ufw` on keeps SSH, the API server and pod traffic working. The learner works as `student` through `astrona ssh astro-ats-033-lab-030-01-02`, runs `sudo ufw deny 19091/tcp` and turns `ufw` on.

Outcomes (1 point each):

- `ufw-deny-rule`: `ufw status` shows `Status: active` and a `DENY` or `REJECT` rule for `19091/tcp`.
- `pod-access-blocked`: `wget` from `shuttle` to the node InternalIP on port 19091 fails with a timeout or `Connection refused`.

Guards: `node-metrics-server` runs on the node, `ss` shows a listener on port 19091 that is not bound to `127.0.0.1`, and `curl` on the node to its own InternalIP on port 19091 returns `Directory listing for /`. That request uses the loopback interface, which `ufw` always accepts, so a rule that blocks everything on the port still passes; a changed bind address does not.

The files under `vm/` are generated by `scripts/ci/vm-lab.py`; regenerate them after any change to a lab file. Run `astrona test` on this folder: `vm/verify-start.sh` checks that every outcome fails on the starting state, then the reference solution is applied and every outcome must pass. Live run on 2026-11-18 (QEMU image `24.04-cks` build 20261118, Kubernetes `v1.35.10`): `astrona test` ended with `PROCTOR: PASS` (2/2). In a separate `astrona run`, `shuttle` reached `10.0.2.15:19091` on the start state; after `ufw deny 19091/tcp` and `ufw --force enable`, `shuttle` got `wget: download timed out`, the node still got `200` and stayed Ready.
