# Bind The Scheduler To Loopback

The lab runs a one-node kubeadm cluster in a QEMU VM (`runtime.type: qemu`). `vm/install.sh` builds the cluster and runs `bootstrap/setup.sh`, which seeds the pod `shuttle`, changes `--bind-address=127.0.0.1` to `--bind-address=0.0.0.0` in `/etc/kubernetes/manifests/kube-scheduler.yaml` and waits until kube-scheduler listens on `*:10259`. The learner works as `student` through `astrona ssh astro-ats-033-lab-030-03-01` and restores the loopback bind address with `sudo`.

Outcomes (1 point each):

- `scheduler-loopback-listener`: the running kube-scheduler command line (`pgrep -a`) has `--bind-address=127.0.0.1`, `ss -tln` shows port 10259 on `127.0.0.1` only, and `curl -sk https://127.0.0.1:10259/healthz` on the node returns `ok`.
- `scheduler-port-closed`: `wget` from `shuttle` to `https://<node InternalIP>:10259/healthz` fails with `Connection refused`.

Guard: the kube-scheduler mirror pod is Ready.

The files under `vm/` are generated by `scripts/ci/vm-lab.py`; regenerate them after any change to a lab file. Run `astrona test` on this folder: `vm/verify-start.sh` checks that every outcome fails on the starting state, then the reference solution is applied and every outcome must pass. Live run on 2026-11-18 (QEMU image `24.04-cks` build 20261118, Kubernetes `v1.35.10`): `astrona test` ended with `PROCTOR: PASS` (2/2). In a separate `astrona run`, `shuttle` got `ok` from `10.0.2.15:10259` on the start state; after the manifest fix kube-scheduler listened on `127.0.0.1:10259` only and `shuttle` got `Connection refused`.
